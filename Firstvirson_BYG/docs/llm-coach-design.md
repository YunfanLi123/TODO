## 0. 一句话

**把「识别」这一层换成视觉语言模型，其余全部保留：**
模式库负责「什么是对的」，模型负责「你做了什么」，内核负责「对不对」，
报告负责「改了就一定变好」+ **对应的那几秒视频**。

```
上传录屏
  ├─ 读时钟（已有，成功）           → 局内时间轴（给模型当锚点）
  ├─ 切窗（已有，规则库倒推）       → 6~8 个「该做什么」的时间窗
  ├─ 抽帧（已有）                   → 每窗若干帧 + 整段轨迹
  └─ ★ 模型读这一窗（新增）         → 「这一窗你做了什么、错在哪」
        ↓
     与操作模式库对账（内核已有）    → satisfied / deviated / undetermined
        ↓
     报告：只给「改了就一定变好」的建议 + 视频片段
```

**用户不再填任何表单**：分路、胜负、BP 禁用与选人，都由模型读出来，**人来核对**。

## 1. 模型这一层怎么接（不新造轮子）

### 1.1 落点已预留好

`app/collection/video.py` 里已经有 `VideoRecognizer` 抽象基类（`detect_round_boundaries` /
`recognize_rounds`），`RecognizedRound` 带着 `facts` / `actions` / `probe_moments` /
`probe_absent` / `video_time`。**新方案只需要实现这个接口**，内核一行不改。

调研的三条路线对应三种接法：

| 路线 | 做什么 | 产出形状 | 适合 |
| --- | --- | --- | --- |
| **A 窗口级事件抽取** | 给模型一窗的帧 + 轨迹，问「这几分钟你在干什么」 | `DetectedAction` 列表（复用 `MOBA_ACTION_VALUES` 词表） | 主力：一次调用覆盖整窗的所有动作 |
| **B 模式级定向问答** | 把模式库当提问清单，一次问几十条 | `Verdict` 三态 | 主力：直接产出「哪条模式没做到」 |
| **C 时间定位优先的两段式** | 先整段粗定位可疑片段，再精读 | 时间戳 | 提速：19 分钟的录屏不必每窗都精读 |

**落地顺序：A → C → B**。A 最容易验证（模型答的词表是我们自己的），C 解决速度，B 解决「模式库那么多条」的覆盖。

### 1.2 必须做的三件事（不做就不准）

1. **ROI 裁剪放大**：王者 HUD 的字太小，模型读不清计时器、击杀数、经济。
   把时钟/顶栏/小地图裁出来放大再喂（我们已经有区域表 `hud_regions.json`）。
2. **不许模型自由发挥**：提问只给**封闭选项**（动作词表 + 位置词表 + 「以上都没有」）。
   自由发挥的输出没法对账，也没法复查。
3. **置信度要自己算，不要信模型自报**：
   同一窗换一次采样再问一次，答案一致才算数；再叠一条「有没有给出可核对的证据帧」。
   合成出的置信度映射到既有的三态阈值（事实 0.30/0.75、动作 0.40/0.75）。

### 1.3 证伪不了的，就不判

模型答「不确定」时，**不许**当成「没做」。沿用现有语义：
`unknown → missing_facts → undetermined → 报告里写「读不出来」`。
这一条已经写进内核，不动。

## 2. 操作模式库：从「死表」变成「能指导」

现在的 1680 条长这样：触发条件（事实 + 阈值）+ 期望动作 + 怎么改 + 理由 + 溯源原文。
它**能判**，但**指导性弱**：只说「你该转线」，没说「转线能带来什么」「不改会怎样」。

### 2.1 每条模式补三个字段

| 字段 | 含义 | 为什么 |
| --- | --- | --- |
| `impact` | 「照这么打能拿到什么」（收益） | 报告要回答「改了就一定变好」，收益必须来自模式原文，不是我们编的 |
| `trigger_nl` | 自然语言的前置条件 | 事实条件覆盖不到的局面（人数、大龙状态、装备差距）交给模型判 |
| `priority` | 重要度（1~3） | 报告只给**改了就有用**的；挑不出来就少说 |

**「不吹毛求疵」就落在这**：一条模式如果 `impact` 说不出收益、或触发条件在画面里看不出来，
就不进报告 —— 宁可少给，也不给「你该注意走位」这种废话。

### 2.2 库放在 GitHub，应用只读

- 模式库是一个**独立仓库**（JSON + 元数据），应用按 `version` 拉取并缓存。
- 用户想改「前期打野该怎么做」→ 改仓库里的 JSON → 应用更新 → 报告立刻变。
- 应用不内置副本（内置只留一份「拉不到时的兜底」，并明确标出这是兜底）。

**为什么是 GitHub 而不是设置页**：模式库是**知识**不是**设置**——
它有版本、有人 review、要能 diff、要能回滚。用数据库表改这类内容，半年后就没人知道哪句是对的。

### 2.3 匹配方式：从「事实条件」扩到「事实条件 + 自然语言」

```
命中规则 = 事实条件全过（机器判，精确）
        AND （没有 trigger_nl  OR  trigger_nl 由模型判为真）
```

`trigger_nl` 由模型在窗口级一起问（路线 A 的提问里顺带带上一批），
命中不了就算「不适用」而不是「没做到」—— 这和内核现有的 `subject` 守卫是同一个道理。

## 3. 报告怎么写（这是产品成败的地方）

现在的报告是「4 条偏离 + 2 条无法判定」。新报告每一条必须凑齐**四件东西**，缺一件就不写：

| 件 | 来源 | 例 |
| --- | --- | --- |
| **看到了什么** | 模型在第几秒看到的画面 | 「2:56 你在中路草丛蹲了 8 秒，对面三人已过河道」 |
| **该做什么** | 模式库的 `title` + `怎么改` | 「先探草丛再进龙坑，别在河道口停 8 秒」 |
| **为什么有用** | 模式库的 `impact`（**原文**，不自己写） | 「这样能先手开龙，把龙 buff 压在对抗路」 |
| **证据** | 视频片段（模型给的时间戳） | 播放 2:40–3:05 |

**不许出现的写法**：
- 「你可能没有注意走位」——没有可核对的画面。
- 「建议保持补刀节奏」——`impact` 里没有收益，就是废话。
- 只给结论不给片段 ——用户没法验证，那等于让模型替玩家编话。

**「该做什么」必须来自模式库**，模型只负责「你做了什么」和「画面里当时是什么局面」。
**分工清楚，责任清楚**：模式库错了可以改库，模型错了能看片段复核。

## 4. 用户要做的动作（目标：接近于零）

| 现在 | 之后 |
| --- | --- |
| 标注页选分路、选胜负 | **模型读出来预填**，用户核对（可改） |
| BP 一环一环自己选禁用/选人 | **模型从 BP 帧读出来预填**，用户核对 |
| 逐段标注动作 | **取消**（本来已取消） |
| 写补充说明 | 保留（可选） |
| 提交 | 保留 |

**「难道还要我自己去选」的答案是：不用，但要你核对。**
分路与胜负模型能从画面读到（结算画面、小地图、键位档位），
但**读错了整局规则会整批不触发**——所以是「预填 + 核对」，不是「不问」。

## 5. 分阶段落地

| 阶段 | 做什么 | 验收 |
| --- | --- | --- |
| **0（现在）** | 复盘 + 调研 + 界面修（对局名、依据文案、片段尺寸、梦琪） | 已完成 |
| **1** | 跑通一个 VLM 识别器：单窗、封闭选项、输出 `DetectedAction` | 在用例2 的「第 2~4 分钟」这一窗上，模型答的动作与人工看片一致 ≥ 6/8 |
| **2** | 接入内核：模型的 `DetectedAction` 走现有 `to_raw_match`，报告能出结论 | 报告能出**≥ 8 条**有片段、有收益、看得懂的建议 |
| **3** | 时间定位两段式（路线 C） | 19 分钟录屏的全量分析 ≤ 3 分钟 |
| **4** | 模式库 GitHub 化 + `impact`/`trigger_nl`/`priority` 三个字段 | 改一条模式的 `impact`，报告能变 |
| **5** | 表单预填（分路/胜负/BP） | 用户不用填任何一项就能提交 |
| **6** | 「百分百改正后就能提升」的筛选器 | 报告里每条建议都能指出「改了什么 → 会带来什么」 |

**阶段 1 的失败判据**：如果模型在王者画面上连「你在哪条路、是不是在打龙」都答不对，
**先解决 ROI 裁剪与画面放大**，不要急着做后端。

## 6. 明确不做的事

- **不训模型**。8×H100 量级的事我们做不了，也不该做。
- **不依赖任何王者域公开数据集**（唯一公开的那个禁商用）。
- **不让模型直接给结论**。模型给「事实与画面」，结论由模式库 + 内核出。
- **不删现有 CV 能力**：轨迹、时钟、区域表、键位档位仍是模型的**辅助信号**与兜底。
- **不为了覆盖率牺牲可信度**：模型读不出来就写「读不出来」。

## 7. 落地记录（2026-10-24）

### 7.1 尖峰结果：模型**读得懂**王者画面

用例2 的「第 2:00~4:00」一窗，8 帧 768px 宽，直接问模型：

| 帧 | 视频秒 | 局内时间（我们算的） | **模型读到的计时器** |
| --- | --- | --- | --- |
| 1 | 302.5 | 02:07.5 | **02:08** |
| 2 | 317.5 | 02:22.5 | **02:23** |
| … | … | … | … |
| 8 | 407.5 | 03:52.5 | **03:53** |

**8/8 读对**（误差全在 0.5 秒以内 —— 那就是四舍五入）。
小地图位置（野区/河道/中路/发育路）与大招状态（亮/灰）也读得出来。

**但它会编**：被问到时它说出了「鲁班七号」「百里玄策」「韩信」「杨玉环」「铠」，
还说了「进行局内语音录入」（录屏根本没有音轨）。
⇒ 提示词里已经写死三条禁令：不许编英雄名、不许编击杀数、不许提语音播报。

### 7.2 三处与原计划不同（都是被现实改的）

| 原计划 | 实际改成 | 为什么 |
| --- | --- | --- |
| 按窗切**视频**发给模型 | **按窗发帧图**（+ 一张合成 HUD 面板） | 机器上没有 ffmpeg；cv2 编不出 H.264（缺 openh264），只有 mp4v，而服务端不认 mp4v（实测「video analysis failed」）。帧我们本来就抽好了，**不用重编码** |
| 复用流水线抽好的帧 | **每窗按 1 帧/10 秒重抽**（4~16 帧） | 阶段抽帧是「一分钟一帧」，一窗只有两三帧 —— 那点画面看不出「在野区来回」还是「路过野区」 |
| 本地 Qwen3-VL-8B | **MiniMax M3 API** | 4 GB 显存装不下 8B；用户已配好的 MiniMax key 走 API 更省事 |

### 7.3 端点与凭据（实测）

- 国内 `https://api.minimaxi.com/anthropic`、国际 `https://api.minimax.io/anthropic`；
  OpenAI 兼容则是 `.../v1`。
- **Anthropic 形状的路由是 `/anthropic/v1/messages`** —— 少写 `/v1` 就是 404（踩过）。
- 两条协议都实现了（`image` 块 vs `image_url` 块），报错像「媒体块不认」时**自动换一条重试**。
- **凭据要用开放平台的 API Key**（platform.minimaxi.com → 账户管理 → 接口密钥）。
  运行时 `config.yaml` 里那个是**占位符**（长度 6），打过去会 401；
  应用里另有 `agent.minimax.cn` 那个是**代理端点**，要的是它自己的 token。
  ⇒ 应用只认 `MINIMAX_API_KEY` 环境变量或**数据目录里的 config.yaml**，
  上传页有个输入框可以直接填（`/api/videos/model-key`）。

### 7.4 模式库：独立 git 仓库 + 可配置来源

`mode-library/` 是一个**独立的 git 仓库**（已初始化并提交），应用按
`MODE_LIBRARY_PATH` → `<数据目录>/mode-library` → `<项目>/mode-library`
→ `app/seed/`（内置兜底）的顺序找它。`/api/games/{game}/rules` 会回报当前用的是哪一份。
内置改了要同步：`python tools/sync_mode_library.py`。

### 7.5 表单预填（分路 / 胜负 / BP）

- 标注页多一个「让模型先读一遍」：读小地图判分路、读结算画面判胜负；
- BP 录入页多一个「从 BP 画面读一遍」：读 BP 阶段抽好的帧，给出禁用与选人。
- **预填 ≠ 替玩家决定**：读不出来就留空，页面上写明「模型读的，请核对」。

### 7.6 还没做完的一件事

**端到端真跑一遍**需要用户自己的 MiniMax 开放平台 key（填在上传页即可）。
没有 key 时：扫描照跑，报告照出，但那一局是「没有自动结论」的诚实报告 ——
**不会**退回旧探测器编结论（用户判过那条路失败）。

用 `tests/test_vlm_recognizer.py` 里的**本地 mock 模型服务**把整条链路钉住了
（客户端 → 识别器 → 映射 → 缺失语义），不花钱、不联网、不需要 key。
