# 自动识别层：调研结论与设计

> 这份文档回答两个问题：**别人是怎么做的**（GitHub 调研），
> 以及**我们照着什么做**（事实逐项可行性 + 落地顺序）。
>
> 背景：用户明确「自动识别层是重中之重」，并会提供**清晰的原录屏**
> （聊天软件转发的压缩版做不了识别，原因见 §4）。

## 1. GitHub 调研结论

### 1.1 直接相关：王者荣耀

| 仓库 | 星 | 可复用的东西 |
| --- | --- | --- |
| [myBoris/wzry_ai](https://github.com/myBoris/wzry_ai) | ★327 | 用 AI 玩王者荣耀。**最有价值**：识别与标定的做法 |

| [john-keith/wzry-map](https://github.com/john-keith/wzry-map) | ★36 | 王者地图的 web 版（可能含地图图，用于小地图→地图坐标） |
| [lulaide/WZRY-audio](https://github.com/lulaide/WZRY-audio) | ★18 | 英雄语音数据集（与本项目无关） |

`wzry_ai` 的两个文件直接印证了我们已有的设计：

**`argparses.py` —— 王者 UI 的位置写成屏幕百分比**：

```python
move_actions_detail = {1: {'action_name': '移动', 'position': (0.164, 0.798)}}
info_actions_detail = {3: {'action_name': '发起进攻', 'position': (0.926, 0.14)}, ...}
attack_actions_detail = {8: {'action_name': '1技能', 'position': (0.71, 0.874), 'radius': 100}, ...}
```

即：**摇杆在 (0.164, 0.798)、技能按钮在右下 (0.67~0.84, 0.48~0.91)、
右上角是信号按钮 (0.926, 0.14)**。它自己的 README 也写着
「理论讲王者的百分比位置是固定的，一般不用改」。

→ 与我们已经在用的「相对坐标 + 标定」是同一套思路，**可以拿来交叉校验**：
我们标定出来的技能按钮位置若与它差得远，就是标歪了。

**`onnxRunner.py` —— 识别器的形状**：

```python
class OnnxRunner:
    def __init__(self, model_path, input_width=640, input_height=640,
                 confidence_thres=0.5, iou_thres=0.4, classes=[]): ...
    def get_max_label(self, image):   # 跑推理 → 取分数最高的类别
```

即 **YOLO(ONNX) 在裁好的区域上分类**，输出 `[x, y, w, h, score, class]`。
不是端到端，是**「固定区域裁剪 → 小检测器 → 逐项判读」**。

它的模型文件**不在仓库里**（`models/` 是空目录，README 指向 QQ 群和网站），
所以**权重拿不到，只能拿方法**。

它还有一个 `showposition.py`：点一下截图上的位置，打印百分比坐标 ——
和我们的 `tools/build_clock_templates.py` 是同一个思路（截图 → 标定 → 模板）。

## 2. 我们要读出什么事实

事实清单**从规则库倒推**（不是拍脑袋）：`app/rules/density.py` 的
`seed_density` 与 `app/collection/window_analysis.py` 的 `seed_windows` 同源扫描
得到的引用情况：

| 事实 | 引用条数 | 能不能自动读 | 怎么读 |
| --- | --- | --- | --- |
| `time_min` | 1681 | ✅ | 已有：计时器数字模板（`clock.py`） |
| `position` | 1681 | ❌ | 对局级，画面看不出来 → 问玩家（已在标注页顶部） |
| `my_hero` | 1596 | ❌ | 同上，问玩家 |
| `gold_diff` | 7 | ✅ | **顶栏金币数字**（左队 − 右队），数字模板 |
| `kill_diff` | 5 | ✅ | 顶栏击杀数字，同上 |
| `has_ult_ready` | 4 | ✅ | 大招按钮上的**冷却覆盖**（变暗 + 扇形扫描），颜色/模板判 |
| `matchup` | 9 | ❌ | 问玩家 |
| **动作事实**（刷野/转线/开龙/带线/惩击…） | 绝大多数规则的 `expect` | ⚠️ **最难** | 小地图定位 + 画面上下文（见 §3） |

**结论**：局内时间的难点在**动作事实**。局势类（金币差/击杀差/大招就绪）
用模板就能读，**不依赖模型**。

## 3. 动作事实怎么读：小地图 + 画面上下文

攻略说的操作，本质都是**「英雄在地图上的位置 + 他在打什么」**：

| 攻略说法 | 画面上的对应 |
| --- | --- |
| 刷野 / 反向开局 | 小地图上英雄点在野区营地，且镜头里有野怪 |
| 转线 / 支援 | 小地图上英雄点从一条线移到另一条（或从野区到线上） |
| 开龙 / 抢龙 | 镜头里是龙坑，且小地图上英雄点在龙坑 |
| 带线拆塔 | 镜头里是线上，且小地图上英雄点在自己那条线的远处 |
| 惩击留到最后 | 大招/召唤师技能按钮的冷却 + 画面里龙被打了 |

于是识别分两路：

1. **小地图 → 地图坐标**（固定区域、固定比例）：
   小地图上英雄的那个点 → 换算成大地图坐标 → 落在哪个区域
   （泉水 / 三路 / 野区 / 龙坑 / 峡谷）。
   需要：一张王者地图参考图 + 小地图的裁剪与缩放关系（标定一次）。
2. **画面上下文**（镜头区域）：当前镜头里是龙坑、野怪、兵线还是塔 ——
   这是 wzry_ai 那个 YOLO 在做的事（classes 是游戏元素）。
   我们的选择：**先用模板/颜色特征做能做的**（龙坑的暗色圆形地形、
   野怪的模型、兵线的小方块），做不了的再上小检测器。

**「不做端到端」的理由**：一条规则要的是「这一段有没有做 X」，
端到端模型给的答案没法复查；而「小地图坐标 + 画面上下文」两条证据
都能指回具体画面，判错时能看出是哪里错。

## 4. 输入必须是**清晰原录屏**

聊天软件转发的视频是**压缩过的**，实测：

| | 原录屏（1080p60 手机） | 聊天软件转发版（实测样本） |
| --- | --- | --- |
| 码率 | 8~16 Mbps | **979 kbps** |
| 手机画面宽度 | 1080 | **217**（缩了 5 倍） |
| 计时器数字高度 | ~15 像素 | **3~4 像素**（认出来是 1111/1144 乱码） |

**信息已经丢了，再好的识别器也读不出来** —— 217 像素宽的画面里，
没有「英雄在龙坑」这个信息。所以：用户给清晰原录屏，是这条路成立的前提。

## 5. 模板视频（2026-10-23 实测）

### 5.1 现在的模板视频

用户提供了三段清晰原录屏，都跑通了全链路：

| | 旧模板 | 中间那版 | **新模板（现行）** |
| --- | --- | --- | --- |
| 来源 | 聊天软件转发 | 聊天软件转发 | **LocalSend（局域网直传）** |
| 容器 | 324×720（竖着录） | 720×322（横屏） | **1280×574（横屏）** |
| 画布 | 720×324 | 720×322 | **1280×574** |
| 占屏 | 100% | 100% | 100% |
| 时长 | 24.6 分钟 | 22.5 分钟 | 22.5 分钟 |
| 帧率 | 30 | 30 | **60.8** |
| 大小 | 141 MB | 163 MB | 938 MB |
| 对局 HUD 就位 | 第 154 秒 | 第 17 秒 | **第 1 秒** |
| **局内时间** | 读不出 | 读不出 | **✅ 读得出** |
| 产物类型 | `moba_slice` | `moba_slice` | **`phase`** |
| 触发规则数 | 9 | 9 | **18** |

**新模板是质变**：画布高 574 ≥ 336，顶栏计时器数字 **12 像素**高，
**过了自动识别门槛** —— 于是走的是「读时钟 → 按阶段抽帧」那条正路，
而不是「读不出时钟 → 按信息密度切时间片」的兜底路。
局内时间准了，带时间窗的规则才真正触发（9 → 18 条）。

实测：`probe_clock` 读到 **573 个时刻（全部采样都读到）**，
**斜率 1.0002**、**残差 ±2.1 秒**、**对局起点 0.8 秒**。
时钟读数与 HUD 检测差 19 秒时，系统**以时钟为准**（那是游戏自己的钟）。

### 5.2 王者会「中心反转」180°（用户提醒，已查证）

腾讯官方《王者荣耀作战指南》原文：

> 「如果你的阵营为红方，为了游戏体验，界面会进行 **180° 旋转**，
> 即你的英雄还是出生在游戏界面左下角，但对抗路和发育路的图标会交换位置，
> 当然，**暴君、主宰、法阵等也会交换位置**。」

要点：

- **玩家永远在左下**（中心反转把玩家固定在蓝方出生点）；
- 但**暴君与主宰在小地图上的位置会互换** → **写死坐标框一定会判反**；
- **观战模式不转**（实测那段 2670×1200 的录屏里绿圈 5 分钟不动，就是观战/回放画面）。

**落实方式**（`app/collection/minimap.py`）：

1. **区域表一律按「蓝方基准」存**，查表前按需把坐标旋转 180°
   （`rotate_180` / `MapGeometry.zone_of(..., flipped=)`）。
2. **怎么判视角**：敌方防御塔是**红色**的，而**颜色不随旋转改变** ——
   红塔集中在**右上**=蓝方视角，集中在**左下**=红方视角。
   只看小地图四周一圈（塔贴边，敌方英雄头像在中间，会带偏）。
3. **分不出来就不旋转**，也不给区域名（`map_is_flipped` 返回 `None`）。
4. **龙坑靠图标外观认**（颜色绝对，不随翻转）：主宰是紫粉色的大龙、
   暴君是金白色的小龙 —— `find_objective_marks`。
5. **对抗路/发育路**：改成**跟着主宰走** ——「更靠近哪条龙就是哪条路」。
   比「上半区=对抗路」好，因为后者只是蓝方视角的样子；红方玩家的地图
   被转了 180°，主宰跑到了下半区，而红方玩家的对抗路也在下半区。
   小地图上**没有法阵图标**（王者小地图只画塔、英雄、野怪、龙坑、兵线），
   所以「法阵所在边路=对抗路」在小地图上用不了 —— 换成「跟着主宰走」之后
   就不需要法阵了，而且**全程不依赖判断阵营**（见 §5.7）。

测试 `tests/test_map_orientation.py`（7 项）。

### 5.3 这批录屏的硬限制

| 限制 | 实测 | 后果 |
| --- | --- | --- |
| 旧两段画布只有 720×322 | 计时器数字实际 **6.7 像素**高 | 低于 7 像素门槛 → 读不出局内时间，阶段要手填 |
| **顶栏没有金币数** | 王者顶栏**默认不显示经济** | `gold_diff` 恒为缺失（**不是** 0） |
| 旧两段顶栏数字太小 | 击杀数只有 8~10 像素高 | 模板要靠**人眼标字形** |
| **HUD 位置跟设备走** | 小地图框：720×324 那段是 x38~143，新模板是 x66~245 | 换设备要重标（已做成标定文件） |
| 新模板顶栏是**两行** | 第一行白字 MM:SS（画布 x 874~906），第二行是击杀数（蓝/红） | 标定要按行分开，别按一行算 |

结论：**画布高 ≥ 336**（约 1080p 手机横屏）才能自动读局内时间。
新模板（574）已达标；旧两段（324/322）达不到。

### 5.4 小地图上的绿色标记：**不是**玩家位置（重要负面结论）

小地图上有一处绿色标记，一开始以为那是「玩家自己的位置」（王者会给
自己的头像加绿圈）。**实测证伪**：

- 在 2670×1200 的高码率原片上，帧 584 / 842 / 868 / 896 秒，
  这个绿圈的**像素位置完全相同**（都是 134,240）—— 它是**固定图标**，
  5 分钟一动不动。
- 而在**玩家自己视角**的录屏（两段模板）里，同一个绿圈是跟着玩家走的：
  开局时它在泉水位 (0.04, 0.95)，之后沿地图连续移动。

两种画面单帧长得一样，光看一帧分不出来。所以识别层用一条**保守**规则：

> **整段都没动过 → 当固定图标 → 不报位置**（记缺失）。

宁可少一条事实，也不给一个错的坐标 —— 错的坐标会把「在龙坑」判成
「在野区」，而报告上完全看不出来。

（代码：`app/collection/minimap.py` 的 `HERO_MOVED_MIN` 与
`recognizer._read_position`。）

### 5.5 顶栏击杀数：机制齐了，**模板没验收**（不启用）

用户提供的**三张地图基准图**已经收进项目：

| 文件 | 是什么 |
| --- | --- |
| `app/collection/map_blue.png` | 蓝色方分路图（法阵在**左上**） |
| `app/collection/map_red.png` | 红色方分路图（与蓝方图互为 180°） |
| `app/collection/map_reference.png` | 带红框标出**法阵**的那张 |

**凡是涉及地图的地方以这几张图为准。**

击杀数的读取链路已经全部做出来了（`app/collection/scoreboard.py` +
`tools/build_scoreboard_templates.py`）：

- 左右两块区域**分开标定**（左队偏蓝、右队偏红，中间的「vs」是白的，
  按颜色天然排除）；
- 字形切分用**列投影**（连通域会把「20」的抗锯齿边缘连成一片）；
- 字形**按自身长宽比**缩放（「1」这种窄字仍然是窄的）；
- 模板**两侧共用**（顶栏左右是同一套字体，只是颜色不同）。

**但模板没通过验收**：在 17 个「肉眼确认过读数」的时刻里只有 **2 个**读对。
两个数字连成一段、一个数字被切成两半的情况还是会有，「1」这种窄字尤其吃亏。

所以 `app/collection/scoreboard_digits.json` 标了 `"已验收": false`，
`load_templates()` **不启用未验收的模板** —— 识别层会把击杀差**记成缺失**，
而不是给一个可能读错的数（读错比读不到危险：数字读错之后，每一条带局势
条件的模式都会判到错误的局面，而报告上只是「没触发」）。

**验收标准**：在 ≥15 个已知读数的时刻上读对 ≥13 个。修法方向是
「按已知读数反推字位边界」——数字的**字距是固定的**，可以直接把
区域按字位切开，不必依赖连通域。

### 5.6 大招就绪：✅ 通了

判据用**按钮中心的色彩饱和度**（就绪时是彩色技能图标，冷却时被灰暗遮罩盖住）：

| 状态 | 饱和度均值（1280×574 实测） |
| --- | --- |
| 就绪 | 84.6 ~ 87.6 |
| 冷却中 | 16.3 ~ 39.5 |

两簇之间**没有模糊地带**，阈值取 60。实测逐秒读出来的切换节奏
（516s → 578s 就绪 **62 秒**）正好等于大招 CD，读数可信。

还加了**去抖**：要连续两帧同状态才承认切换（不抖的话会在 404/408/414 秒
这样快速翻转 —— 那是技能特效造成的瞬时假信号）。

**大招框是「档位敏感」的**：王者键位能自己拖，不同玩家的技能簇能差几十像素
（见 §5.8）。框对不上就**不读**（记缺失），因为读到的是别的按钮，
「就绪/冷却」会变成随机数，而报告上只是「没触发」。

### 5.7 英雄位置与区域判定：✅ 通了，而且**与阵营无关**

| 事实 | 怎么来的 |
| --- | --- |
| `hero_zone` = 主宰坑 / 暴君坑 | 认**图标外观**（主宰紫粉、暴君金白）—— 颜色绝对，不随 180° 翻转 |
| 对抗路 / 发育路 | **更靠近哪条龙就是哪条路**（跟着主宰走，与阵营无关） |
| 中路附近 | 离「左下↔右上对角线」近（180° 旋转不改变这条对角线） |
| 视角判定（红方/蓝方） | 敌方防御塔是红的，颜色不随旋转改变：红塔在右上=蓝方视角 |

**关键推论**：因为区域判定全程不依赖「本局是红方还是蓝方」，
所以**不需要**判断阵营也就不会判反。

小地图上**没有法阵图标**（王者小地图只画塔、英雄、野怪、龙坑、兵线），
所以「法阵所在边路=对抗路」这条判据在小地图上用不了 ——
但换成「跟着主宰走」之后就不需要法阵了。

**绿圈那个坑**：小地图上那圈绿色**不一定**是玩家位置 ——
在观战/回放画面里它是固定图标（实测 5 分钟像素位置不变）。
所以识别层只在它**整段动过**时才当位置报（`HERO_MOVED_MIN`）。

王者顶栏左队（蓝方）的数字偏**蓝**、右队（红方）偏**红**、中间那个
灰白的「vs」两通道差接近 0 —— **按颜色就能把左右分开**，比按位置猜稳
（数字位数变了位置就跟着挪）。

流程已经做成工具（`tools/build_scoreboard_templates.py`）：
抽字形 → 聚类 → 出拼图 → **由人肉眼标号** → 写模板
（`app/collection/scoreboard_digits.json`）。

卡在哪一步：**720×322 的录屏里数字只有 8 像素高**，聚类出来的字形
人眼认不准（0/8/6/9 分不开）。工具与识别层的读取逻辑都已就位
（`app/collection/scoreboard.py`），**只差模板**。

两条解法：
1. 用**更清晰的录屏**（1080p）标模板 —— 模板按 8×12 归一，跨分辨率通用；
2. 顶栏布局在不同录屏里的相对位置**并不一致**（实测：旧模板的击杀数在
   0.697~0.754，另一段在 0.683~0.703），所以**每台设备要各标一次**。

### 5.8 测试用例2（熬隐）：键位不一样了，而且流水线一直在空转

用户又给了一段录屏（`测试用例2-熬隐.mp4`），作为**测试用例2**。

| | 测试用例1（赵云） | **测试用例2（熬隐）** |
| --- | --- | --- |
| 画布 | 1280×574 | **1280×574（一样）** |
| 帧率 | 60.8 | **59.5** |
| 时长 | 22.5 分钟 | **18.8 分钟** |
| 前置内容 | 直接进对局 | **前 175 秒是 BP 禁选** |
| 对局起点 | 第 0.8 秒 | **第 175 秒** |
| 时钟读数 | 573 个时刻，残差 ±2.1 秒 | **428 个时刻，残差 ±0.7 秒** |
| 顶栏时钟位置 | x 874~906 | **一样** |
| 小地图位置 | x 66~245 | **一样** |
| **技能簇位置** | 大招在 (1088, 334) | **大招在 (1016, 350)—— 偏了 74 像素** |

**结论一：BP 前置不影响。** 对局起点是**拟合**出来的（读时钟 → 线性拟合），
不是模板里写死的，所以前面有 175 秒 BP 照样能算准。

**结论二：键位是玩家自己拖的，不是换机型。**
画布、时钟、小地图、底部一排按钮全都对得上，**只有技能簇**偏了 74 像素 ——
这是《王者荣耀》里可以自己拖的**键位**。后果很具体：大招框一旦偏了，
饱和度判据读到的是**别的按钮**，「就绪/冷却」变成随机数，而报告上只是
「没触发」，根本看不出错在哪。

**落实：键位档位（`app/collection/skillbar.py` + `hud_regions.json` 的「档位」）**

1. **跨帧稳定**地检出右下角圆形按钮（Hough 圆检测）—— 单帧里草地上全是假圆，
   但镜头在动时纹理会**缓慢漂移**，所以除了「出现得多」还要看**位置散布**
   （≤14 像素）；真按钮每帧只抖几个像素。
2. 每个键位档位存自己的**大招坐标**与整份按钮清单；
   扫描时拿检出的按钮群去匹配，**匹配上哪档就用哪档**。
3. **一档都匹配不上 → 不读大招**（记缺失，并在说明里写明「键位档位没认出来」）。
   宁可少一条事实，也不给一个偏了 74 像素的框读出来的随机数。

实测：两段录屏分别命中「标准键位」「熬隐键位」，大招就绪判据在两段上都成立
（用例2 的就绪饱和度 105~108 / 冷却 ≤53，与用例1 的 87/16 同样两簇分明）。

**结论三：流水线里的自动识别层从来没读到过帧（真 bug，已修）。**
`_recognize_window` 从 `<base_dir>/<id>_frames/` 读帧，而抽帧写的是
`<data_root>/videos/<id>_frames/` —— 路径不对，**一张都读不到**，
于是识别层「静默」地什么都没产出。表现是：报告里规则大量「未判定」，
而界面只显示「没触发」，**看不出**是路径错了。两条产物路径都中招。

修完之后：用例2 的窗口里能读出 `has_ult_ready`（0:00 窗=False、
2:00~4:00 窗=True）、`hero_pos` (0.031, 0.935)、`hero_zone`=对抗路；
击杀差与金币差按设计记**缺失**（模板未验收 / 王者顶栏不显示经济）。

**结论四：`phase` 产物路径以前不产窗、不跑识别。**
按阶段抽了 16 帧，却直接按「一片一条记录」建骨架，**没有时间窗**，
于是局面类事实一个都进不去。现在 `phase` 也按规则库倒推的窗分组，
每窗做一次综合分析（和 `moba_slice` 路径一致）。

**剩下的缺口（不是 bug，是缺功能）**：报告里大部分规则判不了，
根因是**动作事实层还没有** —— 刷野 / 转线 / 开龙 / 带线这些「画面里在打什么」
读不出来，规则自然无法判定。

### 5.9 操作模式驱动的证据探测器（2026-10-24 落地）

这一节的形态是用户定的：**王者没有回合**，
分析单元是**操作模式项的时间窗**（从规则库倒推），
做法是**拿着操作模式项去帧里找匹配**，而不是先给画面分类再对账。

#### 5.9.1 三态

| 状态 | 含义 | 内核怎么判 |
| --- | --- | --- |
| `found` | 看到了证据 | 做到了 |
| `absent` | 信号**可读**，但明确没有 | 该做而没做 |
| `unknown` | 读不出来 | 无法判定 |

**只有强探测器能给 `absent`** —— 读不出「没有」就不要说「没有」。
这条约束写在 `app/collection/probe_specs.json` 的每条规格里
（`允许判没做`）。

**不需要改内核**：`DetectedFact` 早就区分了「采信但值为空」
（→ 事实成立、值为 None → 内核判偏离）与「未采信」
（→ 进 `missing_facts` → 内核判无法判定）。

**为什么不会误伤**：规则库 1680 条**全部带 `subject`**，
窗口动作不匹配这条规则的前提时判**不适用**（不进分母），
所以探测器只覆盖部分模式项时，最多造成**漏判**，不会造成**假偏差**。

#### 5.9.2 密集帧：顺带采，不另开一趟解码

时钟探测那一趟本来就以 2 秒间隔 seek 扫完整局（用例2 实测 413 个采样点，
实测每次 seek 约 0.017 秒），**顺带**裁小地图、收绿圈候选，边际成本约 8 ms/帧。

> 踩过的坑：`cap.set(POS_FRAMES, 越界)` 时 OpenCV 会**钳到最后一帧**
> 并一直返回成功 —— 不按总帧数收口就是个死循环（实测把一个探针挂到 900 秒超时）。

#### 5.9.3 英雄位置：三个真实的坑

| 坑 | 现象 | 结论 |
| --- | --- | --- |
| **尺寸阈值是按旧模板定的** | 玩家的绿圈实测 **24~26 像素、面积 99~300**，而阈值是「边长 ≤22、面积 ≤120」—— **真标记被直接滤掉**，选出来的是别的绿色小块 | 尺寸阈值改成**按小地图边长的比例**（`HERO_SIDE_FRAC_*`） |
| **亮度分不开** | 玩家标记的绿度峰值有时只有 22，**同一帧的绿色地形能到 116** | 靠**形状**（空心弧）认，不靠亮度：候选宽松收、挑选时空心优先 |
| **龙坑图标颜色会变** | **同一个坑位**不同时刻颜色不一样（t=175 紫粉、t=600 金白），两段录屏同一位置的颜色也不同 | 颜色**不能**用来认哪个是主宰；改用**固定位置**（蓝方视角主宰坑左上、暴君坑右下，名字依据用户给的峡谷全图） |

追踪覆盖率：单帧最强绿块 45% → 修完 **63%**（477 采样点认出 300）。
剩下的 37% 主要是**英雄阵亡**期间（没有标记可画）与遮挡。

#### 5.9.4 区域表：用实测轨迹定，不凭印象

区域框是在用例2 整局 2 秒一帧的**轨迹热力图**上标的：
打野全程在地图左半边（己方上下两片野区），右上角几乎没有。

| 区域 | 判据 |
| --- | --- |
| 己方野区 / 敌方野区 | 野怪点位群 + 河道边界（避开主宰坑，否则在坑里打架会被算成刷野） |
| 泉水 | 自家基地角（玩家永远在左下） |
| 己方高地 / 敌方高地 | 高地塔与水晶一带 |

实测分布：己方野区 59%、主宰坑 13%、暴君坑 8%、敌方野区 17%。

#### 5.9.5 覆盖上限（诚实版）

1680 条规则里，**小地图几何这一类探测器**能覆盖：

| 口径 | 全可判 | 部分可判 | 不可判 |
| --- | --- | --- | --- |
| 强探测器（能判「没做」） | **470 条（28%）** | 177 条 | 1033 条 |
| 加上弱信号（原地不动/游走/回撤） | **877 条（52%）** | 126 条 | 677 条 |

不可判的大头是 `last_hit`（补刀，345 条）与 `engage`（开团，271 条）——
它们要**小兵血条 / 敌我碰撞**的语义，小地图给不了。
**用户已定：本轮不做**（小检测器另立里程碑；唯一公开的王者检测数据集
**禁止商业用途**，素材必须自己标）。

⚠️ 一个负面结论：规则库里 1680 条**全部**带 `subject`，所以部分覆盖
只会**漏判**（判「不适用」），不会**假偏差** —— 这是本方案能落地的关键。

#### 5.9.6 报告里的三处变化

1. **画面里的证据**：「视频 15:23 在泉水停留 9 秒」—— 玩家能回看原画面确认，
   只给一句「没做到」没有用。证据**按这条模式期望的那一类动作过滤**，
   不然一条「该带线」的模式会显示出「在泉水停留」。
2. **「没记录到操作」改成「这一段画面里没看到 X」**：前者听着像玩家没勾，
   后者才是事实（信号可读，画面里确实没有）。
3. **判不了的原因汇总**：「这些操作暂时读不出来，所以相关模式判不了：
   目标处理（3 条）团战处理（1 条）」—— 逐条的「无法判定」看不出**整体**缺什么。

## 6. 落地顺序

| 阶段 | 做什么 | 依赖 |
| --- | --- | --- |
| ① 标定 | 一次性把 HUD 各区域（顶栏数字、技能按钮、小地图、时钟）的**相对坐标**定下来，存成 `app/collection/hud_regions.json` | 清晰原录屏 |
| ② 局势事实 | 顶栏金币/击杀数字（复用 `clock.py` 的数字模板机制）、大招就绪（冷却覆盖） | ① |
| ③ 小地图定位 | 英雄点 → 地图坐标 → 区域分类 | ① + 地图参考图 |
| ④ 动作事实 | 小地图坐标 + 画面上下文 → 动作集合（先模板，不够再上小检测器） | ② ③ |
| ⑤ 窗口综合 | 一窗的若干帧 → 一组事实与动作（这正是「在一个时间区间对帧做综合分析」） | ② ③ ④ |

**任何一环读不出来，就退回标注页问玩家** —— 问的只可能是**那一个窗**，
不是逐片填表。识别层越好，标注页要问的越少。

### 6.1 标注页：**不再逐段标注**（2026-10-24 改）

玩家原话：**「我完全不想标」**。

一局 25 个动作选项 × 6 段 = 150 次点击，而这些**画面里就能看出来**。
于是标注页的「这一段做了什么」整块去掉，改成**只读展示**：

| 原来 | 现在 |
| --- | --- |
| 25 个动作勾选框（每段） | 「系统看到：刷野补经济、转线支援」（只读） |
| 经济差 / 击杀差 / 大招就绪输入框 | 「画面里没看到：推线压塔」/「读不出来：目标处理」 |
| 「这段看不清」 | 保留 —— 系统认错了时玩家能一句话推翻它 |
| 局内时间逐段填 | 由时钟给，按窗回填 |

**仍然要问玩家的只有画面里读不出来的**：分路、英雄、本局结果、对局起点校正 ——
都是**一次性**的选择，不是逐段填表。

**「看不清」的语义要改**（原来会把动作清掉、事实留着 → 内核判「该做而没做」）：
现在是**动作和动作事实一起清** → 判「**无法判定**」。
把「看不出来」当成「没做」，报告里就会出现一条玩家从没下过的结论。

读不出来的那几类（经济差、击杀差、补刀、开团）**不猜** ——
记成缺失，规则就不下结论，报告的「这些操作暂时读不出来」里列出来。

### 6.2 对局起点校正：**重读**，不是平移（2026-10-24 改）

玩家在标注页能改「对局从视频第几秒开始」。这个数是**测**出来的
（对局 HUD 一就位就是 0:00），但每段录屏进入对局的时刻不同，
测得准不准还得人看一眼。

用户原话：**「肯定不能推算啊」**。

这句话否掉的是**把算出来的结果平移一下**的做法。原因是：

> 起点偏了多少，原来那批帧显示的局内时刻就偏了多少。
> 平移旧结论 = 拿错时刻的画面去说那一段的事。

这种错最难被发现 —— 结论的方向全对（该刷野刷了野、该转线转了线），
只是**证据对不上画面**：玩家点「看这一段」看到的是另一段，
而报告上看不出哪里出了问题。

所以校正的做法是**按新起点把每一段重读一遍**
（`app/collection/realign.py`）：

| 步骤 | 说明 |
| --- | --- |
| 重抽帧 | 每一帧按新起点挪到新时刻，**重新从视频里读**（不是挪旧图） |
| 重挑键位档位 | 帧换了，档位可能也变了（`hud_regions.json` 的档位是按帧挑的） |
| 重识别 | 逐窗重跑识别器与探测器；轨迹按**新的窗区间**重切 |
| 重建骨架 | 窗口形状与扫描时一致，直接交给 `build_skeleton` |

**不动的东西**（要说清楚为什么）：

- **局内分钟 `time_min`**：那是规则窗自己的时间轴（窗从规则的
  `time_min between` 倒推），不是测量值 —— 改起点不改它。
- **英雄轨迹**：扫描时按**视频秒**采的，与起点无关；只是切分区间变了。

代价：一次重读要重新 seek 抽帧（几十帧，十几秒）＋逐窗识别。
换来的是报告里每一条结论都对得上它标的那几分钟画面。

前置条件：会话里要留着**视频本身**（`_SESSIONS[...]["video"]`）——
光有摘要没法重读。没有视频时**什么都不做**，绝不退化成平移旧结论。

## 7. 标定工具

照 `wzry_ai` 的 `showposition.py` 与我们 `tools/build_clock_templates.py` 的做法，
做 `tools/calibrate_hud.py`：

```
python tools/calibrate_hud.py <截图.png> --region scoreboard_gold
```

在截图上框出目标区域 → 记下**相对坐标** → 写进 `app/collection/hud_regions.json`。
换机型、换清晰度时**重跑标定**，识别代码不动。

**键位档位另有一个工具**（因为它认的是**整组按钮**，不是单个框）：

```
python tools/calibrate_skillbar.py <录屏.mp4> --start 175            # 只看检出了哪些按钮
python tools/calibrate_skillbar.py <录屏.mp4> --start 175 --name 熬隐键位 --ult 2
```

`--start` 是**对局起点在视频里的秒数**（读时钟能算出来）。
工具跨帧稳定地检出右下角按钮群并编号，`--ult N` 指定第几个是大招，
然后把这一档写进 `hud_regions.json` 的「档位」里。识别代码不动。
